# 결과 신뢰성 감사 — 종합 판정

감사일 2026-08-17. 대상은 출하 라우터 하나
(`src/ossp_router/final_router.py` + `models/final-v1`, 정책 `registry_ref: E049`)다.
근거는 `exp/audit/A*.md`, `exp/ceiling-check.md`, 그리고 리드가 직접 실행한 측정이다.

## 1. 최종 판정

> **조건부 신뢰** — 조회표를 제외한 정직한 Dev 점수는 **0.684318**
> (95% 부트스트랩 CI **[0.656175, 0.710795]**). 누수는 조회표 하나뿐이며 이는
> 규정이 명시 허용한 것이다. 다만 **공개 Dev 점수 0.760284는 성능 지표로
> 사용할 수 없다.**

부정 판정(`누수 확정 — 무효`)은 아니다. 규정 위반은 발견되지 않았고, 채점
파이프라인·데이터셋 신원·비용 계산은 독립 재구현으로 전부 일치했다.

## 3. 누수를 제거한 정직한 점수

**0.684318** — `models/final-v1/lookup.npz`를 빈 배열로 교체한 번들
(`build/bundle-nolookup`)로 공식 채점기를 돌린 값이며,
`exp/registry.jsonl`의 동결 정책 E049(0.6843)를 소수 4자리까지 재현한다.
**즉 registry 기록 자체는 원래부터 조회표를 끈 값이었고 과장되지 않았다.**

조회표는 공개 Train+Dev 2,640문항의 SHA-256(프롬프트) → 실측 outcome을 담고,
실측 적중률은 **train 1760/1760 = 100 %, dev 880/880 = 100 %**다. 따라서 Dev
점수는 예측이 아니라 실측값 되읽기다. 규정
([`CHALLENGE_RULES.md`](../docs/CHALLENGE_RULES.md) §사용할 수 있는 정보)이
"조회표"와 "정확한 프롬프트나 프롬프트 해시를 사용하는 공개 자료 조회"를
명시 허용하므로 위반은 아니다. 문제는 **보고 방식**이었다.

### 3.1 진짜 기준선은 all-light가 아니다

A7이 밝힌 가장 중요한 사실이다.

| 조건 | Dev 가중 최종 |
| --- | ---: |
| all-light | 0.619318 |
| **랜덤 특징** + 비용모델 + 배분기 | **0.656297** ← 진짜 무정보 null |
| 라벨 셔플 + 비용모델 + 배분기 | 0.666515 |
| 실제 모델 (프록시) | 0.673267 |
| 실제 모델 (출하 번들, 조회표 OFF) | 0.684318 |

라벨을 무작위로 섞어도, 특징을 난수로 바꿔도 점수가 붕괴하지 않는다. 이득의
대부분은 점수 예측이 아니라 **비용모델 + 예산 배분기**에서 나온다. 점수
모델의 실제 기여는 **+0.028**이다.

### 6.1 기준선과의 기대값 비교 — 이 제출안의 핵심 방어논리

공식 최강 baseline hash-regex는 0.695369로 본 제출(0.684318)보다 0.011
높지만, 예산 한도에 붙어 있어 초과확률이 크다.

| | Dev 점수 | 등급별 초과확률 | **기대 최종점수** |
| --- | ---: | --- | ---: |
| hash-regex | 0.695369 | 39.4 % / 38.9 % / 49.3 % | **≈ 0.40** |
| 본 제출 (조회표 OFF) | 0.684318 | 0.221 % / 0.000 % / 0.631 % | **≈ 0.68** |

한 등급이 0점이면 가중치 0.3~0.4를 통째로 잃으므로, 0.011을 포기하고 꼬리
위험을 제거한 현재 설계가 기대값에서 크게 우세하다.
